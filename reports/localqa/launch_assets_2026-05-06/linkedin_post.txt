Have you thought about giving your coding agent its own local assistant?

Not a replacement for Claude, Codex, GPT, or OpenCode.

A helper agent for the boring but expensive work around them.

That is what I built with LocalQA.

The problem I kept running into: coding agents are powerful, but they burn context on low-value evidence work:

- raw logs
- repo scans
- browser traces
- DOM dumps
- repeated terminal output
- rediscovering what was already tried yesterday

LocalQA acts as an agent for your agents.

It is a local Bonsai-backed sidecar that collects, compresses, remembers, and verifies local evidence before the frontier model spends context on it.

The model split is simple:

- Frontier model: plans and writes code
- Bonsai: handles local evidence triage and cleanup
- LocalQA: connects logs, browser evidence, repo context, memory, and handoff cleanup into the agent workflow

There are two ways to use it:

1. MCP server
Portable default. One strict tool: local_agent_run.

2. OpenCode plugin
Deeper workflow with native tools, rules, hooks, vault handles, and answer_from_handle.

Launch proof from the current alpha:

- 53.39% fewer fresh input tokens in one real OpenCode provider telemetry A/B test
- 74.04% reduction in controlled A/B workflow benchmark, 3/3 quality gates maintained
- 302,772 -> 8,842 tokens in long-horizon benchmark, 9/9 quality gates, 9/9 memory writes

Repo: https://github.com/Ar5en1c/localqa

Important boundary: if you paste raw logs directly into cloud chat, they already went to the cloud. LocalQA works best when the agent is given paths, URLs, tasks, or evidence handles.

My thesis: coding agents do not just need bigger models. They need local context infrastructure.
